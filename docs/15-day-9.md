# Day 9 — Attempts, scoring and immutable evidence

Day 9 records what a learner submitted and how it was scored. Selected-response answers use the frozen server-side key. Constructed responses wait for an instructor to score every saved rubric criterion. Attempts, scores and evidence have no edit/delete API. Learner state stays unknown until Day 10 applies the evidence under an explicit provisional policy.

3. Repeat the same body: expect 200 and the same attempt UUID. Change the text while keeping the key: expect 409. Add a top-level `score`: expect 422.

5. Authorize with the synthetic instructor credential. Read `GET /api/v1/attempts/{attempt_id}/review-content`: it returns the submitted text, exact frozen task and private rubric expectations.
6. Submit `POST /api/v1/attempts/{attempt_id}/review` with the review body below after inspecting the synthetic answer. Expect 200, `status: scored`, scorer version, reviewer attribution, UTC scoring time and evidence per criterion. The supplied points are a demonstration, not expert grading.
7. Repeat the same review: expect the existing score unchanged. Change its note or criterion points: expect 409. An incomplete criterion set, duplicate code, unknown code, negative/noninteger points or points above the rubric maximum returns 422.

## Selected-response scoring

A selected activity accepts:

```json
{
  "idempotency_key": "168c6958-8158-4bec-9c98-0c5c5dd4a788",
  "response": {"activity_type": "selected_response", "choice_id": "a"}
}
```

The choice must exist in that activity. The server compares it with the private key and awards the saved criterion maximum for a correct answer or zero for an incorrect one. Both outcomes create evidence, using `selected-response-v1`; client score fields are rejected. Instructor scoring cannot replace selected-response results. No answer key or expected rubric text is added to learner reads.

Selected practice appears only when the planner chooses routine automaticity work. The retained unknown-state plan contains a worked example and written whole-task return, so it has no selected-response activity. Pure and MySQL integration fixtures verify the selected path through a replayable internal beginner plan without altering persisted learner state. Day 10 will make evidence-driven planning available to live learners. Worked examples do not accept scored attempts (409); submitting the wrong answer format or an unknown choice returns 422.

## Evidence and transaction contract

Submission requires ownership through activity → plan → enrollment → learner and an approved frozen generation. Draft/rejected activities return 404; corrupted approved content returns 409. Before a new attempt or instructor score, the service replays the pinned plan and validates the sequence/hash. Client identifiers, authoritative scores, scorer versions, timestamps and review attribution cannot override server values. Learner text and code remain data and are never executed.

The UUID idempotency key is unique within an enrollment, including across its plans/activities. The service hashes the activity UUID and normalized typed answer. The same key and answer returns the existing attempt; reuse for different content or activity returns 409. A retry after instructor review returns the same attempt UUID with its current scored representation. A new key records a new attempt. This handles request retries; it does not assert that repeated identical answers are independent learning evidence.

Selected submission commits answer, terminal score and all evidence together. Written submission commits the answer alone; instructor scoring later commits a terminal score and all criterion evidence together. A failed insert returns sanitized 503 and leaves no partial new records. Course → enrollment → plan → generation locking serializes submissions with archival; attempt locking serializes terminal review. Concurrent identical operations reuse one stored result; conflicting payloads receive 409.

Each evidence row retains criterion code, exact skill/domain, points/maxima, provisional tier and `formal_certification: false`. Scorer/rubric version, review scope and attribution live on its terminal score; activity/generation/plan lineage preserves the content hash, context, target/focus, published domain and exact catalog/policy versions. Selected focus evidence is `part_task`; written whole-task evidence is `whole_task`. Part-task success cannot certify the target competency, and whole-task points also do not constitute formal certification.

Submitted answers remain unchanged after scoring. Terminal score retries require the same reviewer, note and criterion points; criterion order may differ. Corrections/regrading are not implemented. A different instructor principal must review; self-review is denied even for principals with both roles. Instructor authority is global for this synthetic prototype, following Day 8; university assignments remain required before real learner use.

Archived courses block new attempts while retaining reads, exact submission retries and pending instructor review. Pagination follows the existing API conventions. The implementation does not enforce sequence completion, apply mastery bands, certify competencies, call an AI provider or use real learner data. Continuity remains Day 11 work; provider integration remains Days 12–13.
