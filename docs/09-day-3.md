# Day 3: domain versions, competencies, and skills

Day 3 gives the platform a structured description of what a course teaches. Later, the learner model will record what each student already knows against these skills, and the planner will use the gaps to personalize their learning path. The first AI model will generate activities from that plan in the later provider milestone.

## Understand the three new resources

| Resource | Meaning | Example |
|---|---|---|
| Domain version | A separately identified revision of a course's learning structure | Draft version 1 of introductory programming |
| Competency | An integrated ability the student should demonstrate | Diagnose and fix a simple program |
| Skill | A specific ability within that competency | Trace variable values or conditional branches |

Every competency belongs to one domain version. Every skill belongs to a competency in that same version. This will let future learner evidence refer to the exact learning structure used for the assessment.

`routine` means the synthetic pilot treats a skill as following a repeatable procedure; `non_routine` marks a skill requiring judgment and problem-solving. `requires_automaticity` identifies routine skills selected for fluency practice. These classifications are provisional authoring choices, not measured student knowledge or approved assessment policy. A non-routine skill cannot require automaticity.

## Run the Day 3 demonstration

From the project directory, with Docker Desktop running:

```bash
# Only needed if local credentials are missing; preserves existing values.
python3 scripts/init_local_env.py
docker compose up --build -d --wait api
docker compose --profile test run --build --rm tests
python3 scripts/demo_day3.py
```

Each demonstration creates a new active course named `DAY3-<unique suffix>`, one draft version, one competency, and five skills. It checks readback, edits the debugging description, rejects learner writes, and rejects a duplicate skill code. It prints resource IDs and leaves the course active so you can use it for Day 4. It does not change earlier demonstration courses. Credentials are read locally and never printed.

| EXPRESSIONS | Evaluate simple expressions | routine | true |
| CONDITIONALS | Trace conditional branches | routine | false |

## Try it yourself in Swagger

Open <http://localhost:8000/docs> and use the local author `API_KEY` in **Authorize**. The **domain authoring** section contains the new routes. All paths below start with `/api/v1`.

1. Use `GET /courses` to find the active Day 3 course, or create a fresh course. Copy its UUID into `course_id`.
2. Use `GET /courses/{course_id}/domain-versions` to inspect the existing draft. To create a new empty version, use POST on that same route with `{}`. The server allocates the next number; creation does not clone earlier content.
3. Copy the draft UUID into `domain_version_id`. GET its `/competencies` and `/skills` lists to inspect the example.
4. To author a new competency, POST to `/courses/{course_id}/domain-versions/{domain_version_id}/competencies`:

   ```json
   {"code": "EXPLAIN_PROGRAM", "statement": "Explain how a simple program produces its output."}
   ```

5. Copy the returned competency UUID. POST to the same version's `/skills` route, replacing the placeholder below:

   ```json
   {
     "competency_id": "<competency UUID>",
     "code": "TRACE_OUTPUT",
     "title": "Trace printed output",
     "description": "Follow execution and predict the sequence of printed values.",
     "skill_kind": "routine",
     "requires_automaticity": false
   }
   ```

6. Edit that skill with PATCH on `/skills/{skill_id}` using `{"title":"Predict and explain printed output"}`. GET the same URL to check the persisted edit. Competencies similarly accept PATCH on `/competencies/{competency_id}`.
7. Try creating the same skill code again: expect 409. Try a competency UUID from another version: expect 404. Switch to the learner key and attempt an edit: expect 403. Restore author authorization afterward.

All lists use `limit` (1–100, default 20) and `offset` (default 0). Domain versions sort by version number; competency and skill lists sort by code. Creation returns 201 with a `Location` header for reading the resource. Authoring is restricted to the course's author while the course is active and the domain is draft. All development roles can read this synthetic domain metadata, including after course archival.

PATCH preserves omitted fields; nulls and empty patches are rejected. Codes are normalized to uppercase. Parent IDs, version numbers, timestamps and lifecycle status cannot be supplied as editable fields. To change a routine skill with automaticity to non-routine, submit both `skill_kind: "non_routine"` and `requires_automaticity: false` together.

## Follow the implementation

Read `app/domain_schemas.py` → `app/domains.py` → `app/models.py` → `migrations/versions/0003_domain_authoring.py`. Input schemas validate requests, routes enforce ownership and version scope, models describe records, and the migration creates the database constraints. `tests/test_domain_contract.py` covers request rules; `tests/test_domains_mysql.py` verifies persistence, isolation, rollback and concurrent version allocation.

Every authoring transaction locks the course first, then the domain when one exists. Course archival uses that same course lock. This serializes edits with archival and allocates unique sequential version numbers. Composite foreign keys also reject a skill pointing at a competency from another version, even if a future code path misses the API check.
