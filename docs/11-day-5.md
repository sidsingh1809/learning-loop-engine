# Day 5: learners, enrollments and isolation

Day 5 creates separate student records on top of the shared published domain. The domain describes the course's skills; each enrollment now holds its own state for those skills. A newly enrolled student has unknown knowledge until evidence or diagnostic work establishes a starting point.

## Run the acceptance demonstration

```bash
python3 scripts/init_local_env.py
docker compose up --build -d --wait api
docker compose --profile test run --build --rm tests
python3 scripts/demo_day5.py --course-id 902a24a1-efa5-4172-a261-527f89e03c63 --domain-version-id 3288966b-a0cf-440b-8520-582f52cc88fa
```

These parent IDs refer to the retained Day 3/4 pilot in this local database. For a fresh database, run `demo_day4.py` to author and publish a synthetic course, then use its printed course/domain IDs. Setup adds missing learner credentials while retaining all existing keys and subjects. Rebuilding the API loads any newly added principal.

The script uses two learner-only development keys from `.env` without printing them. It registers each authenticated learner, enrolls each in the same published version, reads their state, and verifies enrollment retries return the same record. It then tries each learner's key against the other's learner, enrollment and state URLs, including a foreign enrollment under the caller's own path and spoofed identity headers. Every cross-learner request returns 404. The author key returns 403 on learner state.

Measured October 5, 2026: the retained published pilot currently has six skills. The demo created two learners, two enrollments and twelve state rows, all unknown with zero evidence and revision. The automated fixture separately checks a five-skill domain. The migration preserved full snapshots of six courses, four domain versions, four competencies, thirteen skills and five prerequisite links, including publication timestamps.

## Try it in Swagger

Open <http://localhost:8000/docs> and authorize with a learner's key from the local `.env`. The main `API_KEY` is an author credential and cannot use these learner routes.

1. `POST /api/v1/learners` with `{}`. Copy the returned learner UUID. No name, email, subject or learner ID is accepted in the body. First creation is 201; repeating registration is 200 with the same learner.
2. `POST /api/v1/learners/{learner_id}/enrollments` with the published parent IDs:

   ```json
   {
     "course_id": "902a24a1-efa5-4172-a261-527f89e03c63",
     "domain_version_id": "3288966b-a0cf-440b-8520-582f52cc88fa"
   }
   ```

3. Read `GET /api/v1/learners/{learner_id}/enrollments/{enrollment_id}/state`. The response identifies the enrollment/version and returns paginated skills. Each item's learning fields start as:

   ```json
   {"band": "unknown", "evidence_count": 0, "revision": 0}
   ```

4. Switch to the second learner's key. Register that identity, then try the first learner's URLs. They return 404. A missing UUID has the same behavior.

Learner enrollment lists and state reads use `limit` (default 20, maximum 100) and `offset` (default 0). State items sort by skill code. State also includes each skill UUID, domain UUID and UTC `updated_at`; this timestamp initially means the row was created, not that learning was measured.

## Follow the implementation

Read `app/security.py` to see keys resolve to a server-configured principal and the learner-role dependency. Then follow `app/learner_schemas.py` → `app/learners.py` → `app/models.py` → `migrations/versions/0005_learners.py`. The request supplies resource IDs, but `own_learner` resolves the learner UUID against the authenticated subject and `own_enrollment` additionally checks its parent. A UUID or a spoofed role header never grants access.

Enrollment locks course then domain, checks active/published status and course/version scope, then inserts the enrollment and every initial skill state in one transaction. A failure leaves neither an enrollment nor partial states. The existing-enrollment and skill lookups use locking reads so concurrent retries see the newest committed enrollment and enrollment racing publication includes every published skill under MySQL's repeatable-read isolation. Database composite foreign keys independently reject cross-course versions and cross-version states.

Registration and enrollment are naturally repeatable for the same principal and parent pair. Repeating them preserves IDs, timestamps and state. No separate idempotency key exists yet. Each learner currently has one retained enrollment per course; another published version returns 409. Transfers, withdrawal, re-enrollment and instructor-assigned enrollment will need explicit lifecycle contracts. Archived-course enrollment POSTs return 409, including retries, while existing enrollment/state reads remain available.

## Current limits and next session

The API stores synthetic pseudonymous records. Its internal development subject mapping remains linkable; university issuer/subject mapping, retention policy and production SSO are unresolved. Authors, instructors and integration clients receive no learner-data grants. A multi-role learner still accesses only their own records.

State is read-only and the database currently permits only the initial unknown/zero-evidence state. Days 9–10 must extend that constraint deliberately when introducing immutable evidence and transactional state updates. No diagnostic, mastery inference, planner, activity generation or AI call is implemented here.

Verification: 159 checks passed in Python 3.9.21 against MySQL 8.4, with no skips. Tests cover authentication, rejected identity/state fields, object isolation, pagination, published/active enrollment restrictions, cross-version integrity, atomic rollback, concurrent registration/enrollment, retained reads after archival and migration lifecycle. See `verification.md` for measured results.
