# Day 11 — Continuity across sessions

Day 11 adds saved plan/generation history, progress reads, acknowledgment of unscored support, two distinct synthetic contexts and a separate experimental review queue. Resume by reading the saved generation, rather than requesting a new plan. Attempts, scores, evidence and application history retain their original IDs and content.

## Find and resume saved work

All routes below require the owning learner. Missing/foreign IDs return 404, non-learner roles 403, and missing credentials 401. Reads remain available after course archival. Collections use `{items, limit, offset}`, with limit 1–100 (default 20) and offset ≥0.

| Operation | Purpose |
|---|---|
| `GET /api/v1/learners/{learner_id}/enrollments/{enrollment_id}/loop-plans` | Find retained plans, newest `(created_at, id)` first. Each item is the existing full plan representation. |
| `GET /api/v1/loop-plans/{plan_id}/generations` | Find saved contexts and their review status, newest `(created_at, id)` first. Includes drafts/rejections but no content or scoring keys. |
| `GET /api/v1/activity-generations/{generation_id}/progress` | Read ordered step statuses, saved attempt IDs and the first unfinished activity UUID. |
| `POST /api/v1/activities/{activity_id}/completion` with `{}` | Acknowledge an approved, unscored worked example. First acknowledgment returns 201, identical retry 200 with the original UTC timestamp. |

Progress has `generation_id`, `loop_plan_id`, `status`, `next_activity_id` and ordered `steps`. Each step includes its activity ID, position, `status` and `attempt_ids`. The status rules are:

- A worked example is complete after its explicit acknowledgment. Reading it alone does not mark it complete.
- A scored activity is complete after any terminal scored attempt, including a zero-point score. Completion records participation; it does not assert success or mastery. Every attempt remains available, including later pending retries under new keys.
- A submitted written answer without a terminal score is `pending_review`. It remains the first unfinished step until scored.
- An untouched activity is `not_started`.

The generation status is `awaiting_approval`, `rejected`, `in_progress`, `pending_review` or `completed`. Draft/rejected generations have no next activity. Approved generations return the first unfinished activity; a complete sequence returns null. Acknowledgment cannot bypass scoring: selected/written activities reject it with 409. Unapproved activities return 404. Client completion/mastery/score fields are rejected with 422. Support acknowledgment never adds an attempt, evidence, state revision or review reminder.

Progress is computed from durable acknowledgments and immutable attempts/scores within one consistent read transaction. There is no browser-session memory, regenerated content or reset on login. Clients can follow the suggested order; Day 11 does not add mandatory sequencing enforcement to the existing attempt APIs. New acknowledgments are blocked after archival; saved acknowledgment retries and history/progress reads remain available.

## Choose a distinct context explicitly

`POST /api/v1/loop-plans/{plan_id}/generations` now accepts:

```json
{"context_variant": "positive-donations-v1"}
```

The only supported values are `positive-sales-v1` (the default, including `{}`) and `positive-donations-v1`. The sales task sums `[4, -2, 3]` to 7; the charity task sums `[6, -3, 2]` to 8, with donation variables and matching support, questions, answer keys, traces and rubrics. Their generated content hashes and activity IDs differ. All steps in one generation share its scenario, and both contexts retain the saved plan's skill alignment, step order, support, duration and logical target context key.

Generation reuse is keyed by `(plan, generator version, context variant)`. Concurrent same-context requests produce one 201 and subsequent 200 responses with the same frozen sequence. Selecting another context creates a separate candidate rather than overwriting an earlier one. Each context requires its own instructor review before delivery. A rejected context remains in history and cannot be silently regenerated under the same key. Unsupported contexts and extra override fields return 422. A generator that returns a different/mixed context is rejected before persistence.

Original sales payloads, hashes, planner snapshots and fingerprints remain unchanged. Context variety is bounded engineering behavior, not evidence of independent observations, transfer or learning efficacy. Provisional mastery still uses the Day 10 policy and does not require context diversity.

## Experimental review schedule, separate from mastery

`experimental-review-v1` records one current reminder per enrolled skill with scored whole-task evidence. Its fixed interval is **seven days after terminal scoring**, independent of the learner's band, success/failure or last login. The interval is an uncalibrated synthetic engineering choice, not a validated spacing recommendation.

```http
GET /api/v1/learners/{learner_id}/enrollments/{enrollment_id}/reviews
GET /api/v1/learners/{learner_id}/enrollments/{enrollment_id}/reviews?due_only=false
```

The default returns due reminders only. `due_only=false` also returns upcoming reminders. Items are ordered by `(due_at, skill_id)` and include skill, source scored attempt, policy version, UTC `scheduled_at`/`due_at`, `due`, current unchanged `band`, `action: whole_task_review`, an experimental rationale and `formal_certification: false`. The response includes the server's UTC `as_of`. A reminder is due exactly when `due_at <= as_of`.

A newly scored whole-task observation replaces the affected skill's reminder with seven days from that score's timestamp. Equal score timestamps use attempt UUID ordering for deterministic historical replay. A pending written answer, worked-example acknowledgment, selected part-task score, read, login or elapsed time cannot dismiss/postpone a due review. Submission/review/synchronization retries anchor to the original score time, so they cannot shift the due date forward. A zero-point whole-task result still schedules a review and retains its ordinary evidence-based state application.

Scheduling commits with score, evidence, state and application history under the enrollment lock. A schedule-write failure rolls back the complete new scoring transaction; a pending written answer survives. Historical Day 10 applications are retained. Migration adds no inferred learning events or reminders automatically: `POST .../state/applications` with `{}`, next-plan creation or an existing scoring/submission retry backfills reminders from the stored scored evidence without applying state twice. Repeated synchronization has `applied_count: 0` and preserves reminder dates.

The queue exposes review work alongside current progress. It does not alter deterministic planner inputs/prerequisite priority, generate review plans automatically, send notifications, infer time decay, reset secure bands, or claim competency certification. Completing a review requires a new scored whole-task observation; existing exact retries do not count again. University calibration, expert content review and research validation remain outstanding.
