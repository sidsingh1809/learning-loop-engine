# Day 12 — Shared generation providers and first AI integration

Day 12 adds a common `GenerationProvider.generate(snapshot, decision, context_variant) -> GeneratedSequence` contract. `TemplateProvider` wraps the existing deterministic generator; `OpenAIProvider` calls the Responses API with structured JSON output. Both return the same validated activity sequence and use the same storage, instructor review, delivery, attempts and continuity APIs.

Implementation and automated verification are recorded in [verification](verification.md). Actual OpenAI calls from a retained synthetic learner plan succeeded on October 16, 2026. The final packaged suite passed 500 tests without skips in Python 3.9.21 against MySQL 8.4. Mocked provider tests remain separate from the actual API evidence below.

User verification (October 16, 2026): the developer reported completing all Day 12 terminal and Swagger tests. Developer time: **5 hours** (user-reported). Individual manual response payloads were not supplied. The measured results and candidate statuses below describe the implementation verification before this manual walkthrough.

## Provider and model decision

| Setting | Selected value |
|---|---|
| Provider | `openai` |
| Model ID | `gpt-6-luna` |
| API | `POST https://api.openai.com/v1/responses` |
| Adapter version | `track-b-openai-v2` |
| Prompt version | `programming-sequence-v2` |
| Reasoning | `low` |
| Output limit | 8,000 tokens |
| Request storage | `store: false` |
| Template adapter / prompt | `track-b-template-v1` / `template-instructions-v1` |

Selected October 16, 2026. OpenAI describes [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) as its efficient model for focused tasks and documents Responses API and structured-output support. This is an engineering starting point for the bounded programming pilot, not a measured educational-quality ranking. The originally considered GPT-4.1 mini received an [October 14 deprecation notice](https://developers.openai.com/api/docs/deprecations), with GPT-6 Luna as the recommended replacement. No GPT-4.1 candidate or call was created.

The model ID is fixed in the adapter; clients cannot choose a model. OpenAI currently documents `gpt-6-luna` as the request ID, without a dated snapshot. Pinning this ID does not promise unchanging upstream behavior. Frozen candidate payloads and hashes preserve exactly what learners receive. Prompt source files are retained under `app/prompts/`. The first live v1 candidate was rejected after its response instructions incorrectly claimed the activity cannot update learner state. Prompt v2 explicitly keeps internal workflow and learner-state claims out of task instructions; it has a separate `track-b-openai-v2` identity. Historical `track-b-openai-v1` / `programming-sequence-v1` candidates retain their original content, hashes and review history. Future model or prompt changes must also use new identities and preserve historical validation.

## Configure the server

Create a secret key in [OpenAI API keys](https://platform.openai.com/api-keys), then edit the project's ignored `.env`:

```dotenv
OPENAI_GENERATION_ENABLED=true
OPENAI_API_KEY=your-secret-key
OPENAI_TIMEOUT_SECONDS=45
```

Keep the existing application `API_KEY`, development principal credentials and database settings. The provider key is separate from application authentication. Do not put it in a request body, frontend, committed file, screenshot or chat. The server reads it as `SecretStr`; API responses and safe provider errors never return it. Compose passes it only to the API service; migration/test services do not need it. [OpenAI's quickstart](https://developers.openai.com/api/docs/quickstart) explains key creation and server environment configuration.

```bash
docker compose up --build -d --wait api
docker compose --profile test run --build --rm tests
.venv/bin/python scripts/demo_day12.py
.venv/bin/python scripts/demo_day12.py --plan-id a0a269b5-5b49-4463-a5f2-4200f4c5e39f
```

The no-argument demo checks template compatibility and the disabled adapter locally, without an OpenAI request. The plan-ID demo uses the first synthetic learner and instructor credentials from `.env`. It requests an AI draft from the actual saved plan, inspects it as instructor, checks frozen reuse, verifies unchanged learner state/plan, and confirms draft activity delivery is blocked. It prints IDs and the content hash, never credentials. It leaves the new candidate awaiting instructor approval. A 201 indicates fresh generation; a 200 indicates saved reuse and does not claim a new paid provider call. Use the alternate context or another synthetic saved plan when a fresh call is required.

To verify the disabled path over HTTP, set `OPENAI_GENERATION_ENABLED=false`, recreate the API with the same Compose command, and run the plan demo with `--expect-disabled` against a plan/context without a stored AI candidate. Existing AI candidates deliberately remain readable and reusable while disabled.

## Request and review

As the owning learner:

```http
POST /api/v1/loop-plans/{plan_id}/generations
X-API-Key: <learner application credential>
Content-Type: application/json

{"provider": "openai", "context_variant": "positive-sales-v1"}
```

`provider` is `template` or `openai`, default `template`. `{}` retains the existing template behavior. The two existing context variants are supported. Extra fields including client API keys, model IDs and prompt versions return 422. Missing/foreign plans return 404 before invoking a provider. Author/instructor/integration roles cannot initiate learner generation.

New generations return 201 and `Location`; same `(plan, adapter version, context)` retries return 200 with the same frozen IDs/hash. Template and AI candidates for one plan/context are distinct. The generation read/history representation adds `provider`, `model` (null for templates) and `prompt_version`. AI model and prompt selection are server-controlled and stored with each generation.

As instructor, inspect `GET /api/v1/activity-generations/{id}/review-content`, then use the existing `/review` endpoint to approve or reject. AI candidates begin as drafts and remain inaccessible through `/activities/{id}` until approval by a different principal. Answer keys stay instructor-only. Generation itself creates no attempt, evidence, learner-state change or review reminder.

## Validation and failures

The prompt contains the replayed plan, selected synthetic reference scenario, skill bands and versioned policy rules. It excludes learner/enrollment identities, credentials, prior answers and personal profile fields. The first AI adapter is intentionally limited to the same synthetic DEBUGGING pilot and its programming prerequisites. It uses the template reference to ground the code, numbers, answer keys and rubric while generating instructional wording.

The adapter requests a strict JSON schema. Server validation independently checks the saved plan fingerprint, step order, target/focus alignment, activity types, components, support, durations, scenario coherence and rubric structure. The route validates again before atomically persisting a draft. Provider/model/prompt provenance is checked again when reviewing, delivering or scoring saved content. Schema checks do not prove semantic correctness; instructors must inspect explanations, answer keys and rubric suitability. Learning efficacy and expert/university review remain outstanding.

| Failure | Result |
|---|---|
| OpenAI disabled | 503, explicit server enablement message; no network call or template fallback |
| Missing/empty server key | 503, explicit `OPENAI_API_KEY` message; no network call |
| Authentication/model access failure | 503, safe server key/project-access message |
| Quota/rate limit | 503, safe quota/rate-limit message |
| Network failure, timeout, refusal or incomplete response | 503, safe provider-unavailable message |
| Malformed candidate, changed plan or inconsistent provenance/context | 409; no candidate persisted |
| Invalid provider/override fields | 422 |

HTTP uses a fixed HTTPS endpoint, rejects redirects, limits response bytes to 256 KiB and performs one attempt with a configurable 1–60-second socket timeout (45 by default). This timeout bounds socket operations; it is not a durable job deadline or an absolute wall-clock guarantee. Raw upstream error bodies and credential-bearing exception details are not returned. Existing records remain available without calling OpenAI, including after disabling the provider or archiving a course.

## Migration and next scope

`0012_generation_providers` adds provider/model/prompt columns and backfills existing generations as templates, without changing payloads, IDs, content hashes, reviews, attempts or state. No new table or dependency is required; the HTTP adapter uses Python's standard library to retain Python 3.9.21 compatibility. Downgrade refuses before DDL if retained AI provenance would be discarded.

Generation remains synchronous and holds the existing course/plan locks during a new request. HTTP retries after a successful commit reuse the saved result, but a process crash after a provider response and before commit can cause another paid call. Durable jobs, bounded retries, request idempotency and shorter transaction lifetimes remain Day 13. Prompt evaluation and instructor feedback remain Day 14.
