# Day 6: activity library and versioned policies

Day 6 supplies the catalog contract for Day 7's planner: three activity formats, explicit 4C/ID component mappings, and exact versions of learning-science and safety policies. An author creates an immutable draft; a different authenticated instructor can approve or reject it for synthetic prototype use. Consumers see only approved versions.

## Run the acceptance demonstration

```bash
python3 scripts/init_local_env.py
docker compose up --build -d --wait api
docker compose --profile test run --build --rm tests
python3 scripts/demo_day6.py
```

No course or learner IDs are needed; the catalog is global synthetic metadata. The script reads existing author, instructor and learner credentials from `.env` without printing them. Each run uses a random code suffix and retains its records. The migration does not seed or approve content: all demo writes use HTTP.

The script creates two approved policies, three approved activities, one draft policy, one draft activity and one rejected activity. It checks all four components, hidden drafts, rejected unapproved policy references, denied unauthorized reviews, immutable content/decisions, stable review retries and draft/rejected exclusion from lists and direct reads.

The scripted instructor-role action verifies the engineering workflow. It is not a human instructional-design review, an efficacy evaluation or university approval. The stored note explicitly records this distinction. Every version has `review_scope: synthetic_only`; activities have server-set `evidence_tier: provisional`.

## Library and mappings

| Format and example | Components | Conditions and limits |
|---|---|---|
| Worked example: model a complete debugging task | Learning tasks; supportive information; procedural information | Model a whole task, explain non-routine reasoning and offer routine steps just in time. Observation is not independent performance evidence. |
| Selected response: recognize a trace result | Part-task practice | Only for routine skills requiring automaticity and additional practice, after introduction in a meaningful whole task; return to that task afterward. Recognition cannot certify debugging competency. |
| Constructed response: diagnose, repair and verify | Learning tasks | Connect routine tracing with non-routine diagnosis; require instructor review before authoritative scoring. Code execution is disabled. |

Formats and components are different concepts: a format can serve several components depending on instructional use. The official [4C/ID description](https://www.4cid.org/about/) identifies the four components and routine/non-routine and automaticity conditions. These mappings are provisional design choices; the source does not endorse this implementation or its duration estimates.

`app/synthetic_catalog.json` contains fixture definitions shared by tests and the HTTP demo. There is no startup import. The minimal library uses a closed format enum and versioned `activity_variants`, rather than a separate editable activity-type registry. Entries describe purpose, generation guidance, nominal duration and mappings. Delivered prompts, options, answer keys and rubrics come with Day 8. Catalog approval never automatically approves generated output.

## Try the APIs

Open <http://localhost:8000/docs>. All routes require `X-API-Key`.

1. Author key: `POST /api/v1/catalog/policy-versions` using a policy from the fixture. Creation returns 201, Location, a UUID and `review_status: draft`.
2. Instructor key: `POST /api/v1/catalog/policy-versions/{id}/review` with `{"decision":"approved","note":"Reviewed for synthetic prototype use only"}`. Repeat for the other category. Authors cannot review; even a principal with both roles cannot review its own submission.
3. Author key: `POST /api/v1/catalog/activity-versions` using an activity from the fixture plus the exact approved `learning_science_policy_id` and `safety_policy_id`. Both must have the correct category. Mappings and references commit atomically with the version.
4. Instructor key: review through `/activity-versions/{id}/review`.
5. Learner or integration key: `GET /api/v1/catalog/activities` and `/activities/{id}`. Policies use `/policies` and `/policies/{id}`. Draft/rejected direct reads return 404.

Authors and instructors inspect review work through `/activity-versions` and `/policy-versions`: authors see their own submissions; instructors see all. Learner/integration keys get 403 on authoring URLs, even for approved content. Approved metadata grants no access to learner records.

Versions are explicit positive JSON integers supplied by the author, at most 2,147,483,647. Codes normalize to uppercase. Uniqueness is `(code, version)` for activities and `(category, code, version)` for policies. Authorized authors can contribute new versions to this shared catalog; provenance is per version, with no exclusive code-family ownership. Duplicate creation returns 409. Creates have no idempotency key: inspect the author's list after an uncertain response before retrying.

There are no PATCH or DELETE operations, including for drafts. Correct content or mappings by creating and reviewing a new version. Approved lists return every approved version in `(code, version, id)` order; there is no silent supersession or latest-version selection. Consumers must persist exact IDs. New policy versions do not change an older activity's pinned policies.

Review transitions once from draft to approved or rejected, with server-controlled reviewer, UTC time and note. Repeating the exact decision/note by the same reviewer returns the unchanged representation. Any different decision, note or reviewer after review returns 409. Concurrent reviews serialize on the version row. Rejection is terminal; create a new version to revise. Revocation/retirement needs a separate lifecycle contract before rollout.

Lists use `limit` (default 20, maximum 100) and nonnegative `offset`. Approved activity lists filter by `activity_type` and `component` with AND; policy lists filter by `category`. Authoring lists filter by `status`, and policy authoring also by `category`. Filtering precedes pagination; component filtering returns full versions with all mappings. Consumer routes always require approval regardless of extra query parameters. Pagination does not promise a snapshot across requests.

## Policy boundaries

Learning-science rules preserve unknown knowledge, whole-task context, return after support, non-routine supportive information, just-in-time routine procedures, automaticity-only part-task practice and fading with evidence. Part-task success cannot certify competency; the prototype cannot award formal certification. No mastery threshold or spacing formula is invented.

Safety rules require synthetic data, learner input treated as data, generated content held untrusted until validation/review, disabled code execution, forbidden client-authoritative scores, instructor review for constructed responses and university review before real use. Missing/unknown rules, category mismatches and relaxed boundaries are rejected. Required references are nonempty bounded provenance strings; they are not automatically fetched or validated endorsements.

These are stored contracts for subsequent modules. Day 6 has no planner, generator, scorer or runtime policy evaluator; Days 7–10 must enforce the relevant rules in their own operations/tests. Approval checks schema, role, attribution and policy references. An instructor remains responsible for substantive content review; schema validation cannot determine educational quality, accessibility or free-text safety.

## Implementation and measured results

Follow `app/catalog_schemas.py` → `app/catalog.py` → `app/models.py` → `migrations/versions/0006_catalog.py`. The additive migration creates `policy_versions`, `activity_variants` and `component_activity_mappings`; migrations 0001–0005 are unchanged. Foreign keys retain references, mapping keys forbid duplicate components, and checks constrain format/category/component, version/duration, scope and review attribution. JSON shape, approved policy categories, nonempty mappings and immutability are API invariants, not SQL triggers.

On October 7, 2026, all 231 checks passed in Python 3.9.21 against MySQL 8.4, with no skips. The live HTTP demo retained run suffix `_B3C50883`, with three approved activity definitions and both policy categories. Full row hashes matched across the local migration for six courses, four domains, four competencies, thirteen skills, five prerequisite links, two learners, two enrollments and twelve learner-state rows. The local API and database are healthy. See `verification.md` for evidence.

University curriculum, policy, privacy/retention, accessibility and assessment owners must review these inputs before a real cohort. Next session: Day 7 deterministic planning using the published graph, isolated learner state and exact approved catalog/policy IDs.
