The synthetic API loop now closes: saved plan → reviewed activities → attempt → terminal score/evidence → learner state → next plan. Selected scoring applies immediately. ## Provisional mastery policy

`provisional-mastery-v1` is a fixed, versioned engineering policy for synthetic data. Its thresholds have not been calibrated or approved by the university. It is separate from the pinned learning-science and safety catalog versions; the state snapshot and application history retain its version. There is no policy-override request field.

| State or measure | Rule |
|---|---|
| `unknown` | No applied evidence, revision zero, policy version null. Unknown does not assert low proficiency. |
| `developing` | At least one applied criterion, including a zero-point result, without meeting the secure rule. |
| `secure` | At least two scored whole-task attempts for this skill, with at least 80% of cumulative whole-task rubric points. |
| `evidence_count` | Number of applied rubric criteria for the skill. |
| `revision` | Number of applied scored attempts affecting the skill; multiple criteria in one attempt increment once. |
| `whole_task_evidence_count` / `part_task_evidence_count` | Separate criterion counts. Their sum is `evidence_count`. |
| `whole_task_attempt_count` | Scored attempts containing whole-task evidence for this skill. |
| `whole_task_points` / `whole_task_max_points` | Cumulative whole-task points/maxima only. Part-task points never enter this ratio. |

A successful first whole-task attempt produces developing state. A second full-credit whole-task attempt can produce secure state. Repeated part-task success alone cannot produce secure state. Further poor whole-task evidence can lower the cumulative percentage and return a skill to developing; evidence/history remain intact. Part-task evidence preserves an already justified secure band but cannot supply its threshold points or required whole-task attempts.

Whole-task criterion evidence can describe either the target or a prerequisite demonstrated within that task. A skill band is not competency certification. All state/application responses retain `formal_certification: false`. The planner still considers unresolved prerequisites before the target, so secure target evidence does not skip unrelated unknown prerequisites in its required graph.

New idempotency keys record new attempts, even on identical content. The policy does not establish independent observations, context diversity, calibrated confidence, time decay, review scheduling or genuine learning efficacy. This limitation matters because repeated attempts on one template can meet the provisional threshold. Policy changes require a new version and explicit migration/reapplication design; existing history is never silently rewritten.

## API and transaction contract

Attempt submission, score validation and authorization retain Day 9 semantics. Every attempt response adds `state_application`: null while pending or before historical synchronization; otherwise it contains the attempt/enrollment/domain, policy version, UTC application time, false certification flag and per-skill changes. Each change names the exact criterion codes and before/after band, counts, revision and policy. The score's immutable evidence supplies the criterion points/kinds; the attempt links to the frozen activity, plan, catalog and policy provenance.

Selected submissions commit the attempt, score, complete evidence set, states and application marker together. Written submission commits its immutable answer; instructor scoring later commits score/evidence/state/history together. A failure in evidence insertion, a state update or history insertion returns sanitized 503 and leaves no partial new work. A failed written review retains the pending answer. Retry after failure can complete the transaction.

The application primary key is the terminal attempt UUID. Course → enrollment locking precedes attempt/state mutation in submission, review and synchronization, preventing lost revisions and duplicate application under concurrent requests. Current locking reads see committed updates after waiting under MySQL repeatable-read. Different attempts add separate revisions; same-key submissions and identical reviews reuse the stored result. Changed retries remain 409. Application history has no edit/delete endpoint. Reads do not change state.

`POST /api/v1/learners/{learner_id}/loop-plans` synchronizes stored unapplied scores before taking its input snapshot. It then runs the existing deterministic planner. A changed revision/policy/band produces a new fingerprint; identical current inputs reuse the saved plan. The scoring response does not automatically create the next plan: clients request it with the desired target, budget and exact approved policies. Failed planning rolls back synchronization performed in that request.

## Existing Day 9 records

The migration adds counters/history and relaxes the initial-only band constraint; it leaves existing state values, attempts, terminal scores and evidence unchanged. Pending historical answers still wait for review. Existing scored evidence is applied on scoring/submission/review retries or next-plan creation. A learner can also synchronize explicitly:

```http
POST /api/v1/learners/{learner_id}/enrollments/{enrollment_id}/state/applications
X-API-Key: <own learner credential>
Content-Type: application/json

{}
```

The 200 response contains `enrollment_id`, `applied_count`, `policy_version` and `formal_certification: false`. Repeating after synchronization returns `applied_count: 0` and changes no state or evidence. Only `{}` is accepted; a supplied band, policy or evidence returns 422. Another learner receives 404; non-learner roles receive 403. Archived enrollments retain synchronization and pending review, while new attempts/plans remain blocked.

Unapplied scores are processed by `(score.created_at, attempt.id)` within the synchronization transaction. Each score's evidence is grouped by skill, and every affected skill receives one revision. The operation reuses saved evidence rather than rescoring or regenerating content. A batch failure rolls back every application in that request. No client-authoritative state write exists.
