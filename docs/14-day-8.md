# Day 8 — template activities from saved plans

Track B turns a saved Track A plan into a frozen activity sequence. It preserves step order, exact catalog/policy versions, focus/target alignment, support, full durations and shared whole-task context. A supported plan starts with a worked example, optionally practices a routine prerequisite, and returns to the same whole debugging task. The generator does not score attempts or update learner state.

## Run the walkthrough

```bash
docker compose up --build -d --wait api
docker compose --profile test run --build --rm tests
.venv/bin/python scripts/demo_day8.py
# Use the retained Day 7 plan, owned by the first configured synthetic learner:
.venv/bin/python scripts/demo_day8.py --plan-id d4022c31-de90-4a82-bffa-3f9b9cda8bc9
```

Without a plan ID the script demonstrates internal unknown, beginner and experienced fixtures. With an ID it consumes the saved plan over HTTP, checks the candidate, performs an attributed development-instructor review, and reads delivered content. The review is programmatic and synthetic; it is not substantive expert or university approval. It also checks retries, blocked learner review, isolation, private scoring keys and unchanged learner state. It reads local credentials without printing them.

## API walkthrough

1. As the owning learner, send `POST /api/v1/loop-plans/{plan_id}/generations` with `{}`. First creation returns 201 and Location; identical plan/generator retries return the saved generation with 200. The body accepts no client content, support, provider, scoring or review override.
2. Read `GET /api/v1/activity-generations/{generation_id}` as the owner. This contains review/provenance metadata and activity UUIDs in plan order. Before approval, `GET /api/v1/activities/{activity_id}` returns 404.
3. As an instructor, inspect `GET /api/v1/activity-generations/{generation_id}/review-content`. This exposes the full typed candidate and rubric, including private answer keys. Development instructor authority currently covers synthetic candidates globally; real learner review requires institution assignments and privacy approval before rollout.
4. As that instructor, send `POST /api/v1/activity-generations/{generation_id}/review` with `{"decision":"approved","note":"Synthetic content and rubric inspected."}` or `rejected`. The review applies atomically to the connected sequence and records reviewer, UTC time and note. A different principal must review. Identical reviewer/decision/note retries preserve attribution; changed terminal review returns 409.
5. As the owning learner, read each approved activity through `GET /api/v1/activities/{activity_id}`. The typed `step` includes prompt, scenario, catalog ID, skills, components, support, duration and rubric criteria. Selected-response keys/explanations and expected rubric answers stay private. Worked-example explanations are intentionally visible as instructional support.

Other learners receive 404 for generations, activities and generation requests on a foreign plan, including approved activities. Author/integration roles have no learner grant; review requires instructor authority. There are no content edit/delete routes. A rejected generation remains rejected on retry. Correction needs a newly versioned server template or a revised saved plan, not a mutable retry body; template version selection is currently internal.

Missing/inaccessible IDs return 404. Unsupported pilot content, corrupt saved ordering, invalid adapter output, changed provenance or invalid rubric return 409 before any generation is saved. Database failure returns sanitized 503 and rolls back the entire candidate. New generation on an archived course is blocked; existing generation retries and reads remain available.

## Template and schema contract

`track-b-template-v1` uses the bounded `positive-sales-v1` Python-text case: a shop should sum positive sales `[4, -2, 3]`, but `total = sale` replaces the running total and prints 3 rather than 7. The whole task asks for a repair, trace and explanation. Variables, expressions, conditionals, loops and debugging each have explicit focus support. Selected-response automaticity questions exist for VARIABLES and EXPRESSIONS only. Code is never executed.

This first template supports a non-routine `DEBUGGING` target and the named routine prerequisites in the synthetic programming pilot. It is not a general content generator for arbitrary courses. The API rejects unsupported targets/foci rather than supplying unrelated material. Skill codes/classifications are the prototype template-selection contract; substantive curriculum alignment still requires expert review. Provider/model integration remains scheduled for Day 12.

Content uses a discriminated union of worked example, selected response and constructed response. Strict inputs reject extra fields, empty/bounded text violations, duplicate choice IDs, missing answer keys, malformed rubrics, point-total mismatches and forbidden certification. Worked examples are unscored; selected responses have a keyed focus criterion; constructed responses require instructor review and cover both the requested target and prerequisite focus. `synthetic-rubric-v1` uses illustrative points, not university-approved grading or mastery thresholds.

A separate validator replays the saved plan from its pinned snapshot, then checks every generated position, role, skill, catalog ID, component, support level, duration, format, context key and policy ID. It verifies whole-task target/focus rubric coverage and procedural/supportive content consistency. Structural validation cannot establish teaching accuracy; candidate review is still required under the pinned safety policy.

## Persistence and boundaries

Migration `0008_generation` adds `activity_generations` and `activities`; earlier migrations remain unchanged. One candidate is retained per plan/generator version, with template version and SHA-256 of the complete canonical sequence. Activities retain their exact plan position through composite foreign keys and store validated payload JSON. Plan locking serializes concurrent creators under MySQL repeatable-read. The complete candidate commits together.

Review checks the stored sequence and hash again before approval. Delivery revalidates the approved sequence and hash; corrupted content is withheld. The hash identifies content, including rubric keys; it is an integrity check against accidental changes, not a signature against a malicious database writer.

Learner state still starts and remains unknown until authoritative evidence processing is implemented. No attempt submission, scoring, state update, AI provider call or real learner data is introduced in Day 8. Sequence completion/resumption will be added with the attempt and continuity milestones.
